100: 摘  要
101: 近年来，消费者对穿着舒适度与个性化风格的关注度持续上升，传统大码服装销售模式逐渐显现出与当前多元需求不相适应的问题。在大码服装选购场景中，消费者常遭遇尺码选择困难、购买流程繁琐、售后服务体验欠佳等困扰；而商家则在商品上架效率、订单处理速度及客户关系维护等方面存在明显短板。针对上述问题，开发了“依依大码服装在线销售系统”。该系统的目标是为消费者提供便捷的大码服装浏览与购买渠道，同时协助商家高效完成商品管理、订单处理和客户服务，从而缓解买卖双方的信息不对称，提升整体交易效率。
102: 该系统采用前后端分离的架构设计。前端基于Vue 3框架与uni-app跨平台技术实现，后端则使用Node.js/Express技术栈构建各功能模块。数据存储方面，以MySQL作为主数据库，并引入Redis缓存来提升数据访问速度与一致性。系统功能覆盖商品管理、订单管理、商家入驻管理、用户管理、社区互动、数据统计、优惠券管理及售后管理等模块，基本囊括大码服装线上销售的主要业务环节。本文对该系统的开发过程进行了完整描述：先梳理大码服装电商的典型业务流程，然后从商家与消费者两类用户的实际需求出发，完成系统需求分析，确定各功能模块与数据库结构。基于此，逐一完成各功能模块的详细设计与实现。最后通过若干测试用例对系统进行验证，确保其能够有效满足商家与消费者的日常使用需要。

105: ABSTRACT
106: The population of plus-size consumers is growing steadily, yet general-purpose e-commerce platforms fall short in areas such as size parameter configuration and after-sales process tracking.This paper designs and implements an online sales system tailored for plus-size clothing.The system adopts a front-end and back-end separation architecture,with the back-end API layer built using Node.js and Express, the admin panel using Vue 3,the mobile client developed cross-platform with uni-app,and the data layer using MySQL.This technology stack was chosen primarily for the maturity of each component in its respective role and the smooth integration among the three.
107: On the merchant side, the system implements functions step by step along the business chain:merchant application and onboarding, store management, product listing, order processing, and after-sales management. Notably, the product listing module handles the customization requirement for size parameters separately, extracting them from standard templates and treating them as independently maintainable data units for merchants. The after-sales management module is connected to the buyer-side after-sales inquiry portal, so that once the return/exchange status changes on the merchant side, buyers can see the update simultaneously. The remaining buyer-side features—registration, product browsing, shopping cart, and order placement—are built following the conventional transaction flow without unnecessary complexity. All modules have passed functional testing item by item after development, and the system is running stably.

110: 第1章  绪论
111: 1.1 课题研究背景
112: 服装零售在电子商务版图中分量很重，在线销售系统做到什么程度，直接决定了商家的运营效率和消费者的感受。市面上绝大多数的服装电商方案多数采用通用化平台架构，这种“一套系统服务所有人”的思路，一旦碰上体型特征比较特殊的消费人群，不匹配的地方就变多了[1]。一个很直观的数据是，我国成年人里超重和肥胖的比例已经超过了一半。对于如此庞大的消费群体而言，线上购衣的首要难题在于标准尺码表难以精准适配其体型特征，导致许多人不得不陷入反复查阅尺码与频繁退换货的循环之中[2]。对于服装电商来说，尺码不对是造成退货的首要因素。它带来的不只是逆向物流的成本，还包括无法挽回的客户流失，这是整个行业长期以来没能很好解决的一个老问题[3]。
113: 从销售管理的角度去观察，通用型系统真正的短板，是它对特定品类的运作逻辑缺少细致的关照。大码服装的款式和尺码组合，其复杂程度远不是常规服装可比的。商家如果硬要套用标准化的管理工具，操作上感觉繁琐仅是表层问题，更核心的问题出在信息传递上——那些详尽的尺码参数很难原原本本地抵达消费者，售前咨询量突然增大、售后产生各种分歧，根源往往就在这里[4]。另外再看订单处理和售后，这两个环节普遍缺少一种可见的流程追踪和能够灵活变化的状态流转。结果就是，沟通上花费的成本居高不下，退换货的周期也拉得很长，店铺的运营效率和客户满意度双双被拖低[5]。前面的这些情况其实都指向了同一个需求：为大码服装这个品类专门做一套在线销售系统，用设计好的功能把这一整条线串起来。这件事的意义在于，它能直接改善这个特定人群的购物体验，也能让商家实现数字化运营水平的显著提升。
114: 1.2 课题研究现状
115: 国外大码服装品牌在线上销售上起步较早。Torrid、Universal Standard等搭建的自有平台，已经把尺码匹配和个性化推荐功能深度融合——采集用户体型数据、给出尺码建议，这套做法对降低退货率的效果有实际运营数据支撑[6]。技术实现上，高并发访问下的架构设计、微服务化的订单处理、库存的自动调度，这几个方向论文和落地案例都不算少。但这些系统的运行基础是当地成熟的数据设施和第三方物流售后网络，直接移植到国内市场并不现实。
116: 国内关于在线销售系统的研究，早先多集中在用Spring Boot、SSM这类Java技术栈完成通用商城的功能搭建[7]。等到电商竞争转向精细化运营，研究的关注点开始散开。一部分往特定环节的深处走，像用深度学习做库存需求预测，或者围绕逆向物流搭建信息追踪系统[8-9]；另一部分则放在前端体验和跨平台开发上，出现了基于Vue.js的响应式商城前端、基于uni-app的移动电商应用开发等尝试[10-11]。专门面向特殊体型群体的系统设计，目前能看到的成果很少。已经做出来的系统，大多直接借用了标准尺码模板，尺码参数没办法灵活调整，商家在复杂商品信息管理上的需求被架空了[12]。售后环节的情况类似：状态可视化程度不足，退换货流程缺乏灵活性，这两点会直接反映在运营效率上[13]。售后处理是不是及时、规范，作用于消费者下次还愿不愿意买，对用户留存的影响是根本性的[14]。至于怎么把售后闭环追踪和销售系统从底层打通，现在还是一个缺少研究的地方[15]。这个系统要做的，正是去填这些空缺。
117: 1.3 课题研究目的和意义
118: 本课题围绕“依依大码服装在线销售系统”的设计与实现展开。系统需要同时回应两类需求：对消费者而言，是提供一个尺码信息清楚、交易流程不繁琐、售后处理进度可查的购物环境；对商家而言，则是解决大码服装尺码组合复杂、信息难以灵活管理以及订单售后流转效率偏低的问题。技术路线采用前后端分离，核心涉及Node.js、Vue 3、uni-app和MySQL，目标是交付一套功能完整、交互衔接流畅的在线销售系统。
119: 这项工作的价值，可以从实际应用和功能设计两个方向来看。在应用端，它试图把通用电商平台与大码服装消费场景之间长期存在的错位拉近一些。系统允许商家按自身货品特征建立弹性的尺码规则，并把原本静态的尺码表转换为消费者能直接感知的规格信息，这样做的预期效果是压缩选购过程中的不确定性，减少纯粹因尺码不合产生的退换。对商家，系统通过数据看板和订单管理功能把零散的销售记录提炼为可辅助备货与营销判断的信息，让大码服装的经营有数据可依，往精细化方向移动。在功能设计端，系统在尺码配置、售后状态追踪等环节上所做的定制尝试，其方案本身对后续需要为特定消费群体做深度适配的在线销售系统，也构成一个可供参照的实例。

123: 第2章  需求分析
124: 2.1 任务目标
125: 本系统的使用者分为两类：一类是买家和商家，这是系统的核心用户；另一类是超级管理员、运营和客服，属于后台管理人员。买家通过移动端购物，商家管理自己的店铺和商品，后台人员负责日常运营和用户服务。
126: 买家可浏览与搜索大码服装，使用服装推荐等功能辅助选购，将心仪服装加入购物车，领取并选择是否使用优惠券后结算，随时查看订单物流与售后进度，同时可通过在线会话实时咨询客服。商家提交资质并通过审核后，即可开设店铺、上架服装、管理订单与售后、自主发布店铺优惠券，实现线上自主经营。超级管理员负责审核商家入驻、管理用户，由运营基于经营数据制定运营策略、管理轮播图与，监控社区内容并发布平台优惠券，维护良好交易环境。
127: 2.2 业务需求分析
128: 2.2.1 用户特点
129: 本系统的用户群体涵盖大码服装销售相关的各类人员，具体分为买家、商家、超级管理员、客服和运营五类。其中，买家注册登录后可以浏览商品、加购物车、在线咨询、下单支付、查看订单、申请售后；商家申请入驻本系统后可以管理店铺、管理服装、管理订单、处理售后；超级管理员的工作主要有审核商家入驻申请、管理用户、管理服装分类；客服处理买家的售前咨询和售后问题；运营主要负责查看数据统计、发布优惠券、管理社区内容、管理轮播图。
130: 2.2.2 问题描述及现状
131: 大码服装电商在传统的运作方式下，各环节的衔接是比较零散的。商家入驻时，资质材料通常通过邮件或社交软件提交，审核到哪一步无从追踪，只能被动等通知。服装信息和订单数据分散在不同的文件里，想做一个简单的销售统计都需要手工翻找汇总。售后环节的问题更突出一些，退货申请往往要经过多轮人工转达才能落实，买家寄回商品后，商家有没有签收验货、是否同意退货、退款，这些信息很难实时掌握。
132: 市面上现有的通用型多商户电商系统，虽然能跑通基本的交易流程，但放到大码服装这个市场里看，有几个不太匹配的地方。一是权限划分比较粗，运营、客服、商家等不同角色的操作边界不够清晰，实际操作中容易出现误操作或者越权访问的情况。二是不同商家的数据在后台混在一起展示，缺乏必要的隔离，这对商家来说存在一定的数据安全隐患。
133: 针对这些问题，本系统的设计思路是把散落的人工流程收拢到线上，形成闭环。商家入驻时，提供一个标准化的在线申请入口，审核流程设置了可视化的公告，商家可以随时看到自己的申请是什么状态。服装信息管理和订单流转全部线上完成，从发布、库存同步到订单状态更新，不用再靠表格和聊天记录来跟进。售后方面，我们从买家申请退货、商家审核、买家回填物流单号，到商家同意退货、同意退款，设计了一整套逆向流程。权限管控上，采用了基于角色的访问控制模型，为运营、客服、商家各自配置独立的后台页面，不同商家之间的数据在底层就做了隔离，从源头规避误操作和越权的问题。简单来说，就是把这套系统的运营基础从依赖人工协调，转变为靠数据、流程来驱动。
134: 2.2.3 适用范围
135: 本系统的服务对象是大码服装消费者和入驻商家，后台管理工作则由超级管理员、运营和客服共同承担。部署方式上，系统运行在本地服务器上，用户端不需要安装额外软件，通过普通电脑浏览器或移动端即可访问。对硬件的要求不高，日常使用的智能手机就能流畅操作，网络方面保持稳定的互联网连接即可满足正常使用。

137: 图2-1展示了系统整体业务流程，涉及超级管理员、商家、买家、客服和运营五类角色。超级管理员负责维护基础数据并审核商家入驻，拒绝不符合规范的申请。商家发布商品、管理库存、处理订单及售后管理，售后不通过需说明理由。买家注册登录、下单支付，可确认收货或发起售后。客服为买家解答咨询。运营查看数据、发放优惠券，分析售后原因等。正逆向流程已在图中完整展示，退货原因反馈给商家，形成持续优化。

140: 2.3 系统功能需求
141: 2.3.1 购买服装管理功能
142: 1、需求描述

203: 3.1 构架设计
204: 3.1.1 系统构架
205: 本系统面向买家、商家、超级管理员、运营和客服五类用户，功能上需覆盖服装展示、在线交易和后台管理三大板块。不同角色的需求各有侧重：买家需要浏览、搜索、下单、支付、物流查询和售后申请等完整的购物流程；商家负责服装上架、库存管理、订单处理和经营数据查看；超级管理员承担用户管理、商家入驻审核和权限分配；运营查看销售数据制定运营计划、设置优惠券和设置推荐服装的轮播图；客服在后台解答买家咨询。
206: 前端采用uni-app作为跨端开发框架构建移动端应用；PC管理后台基于Vue 3+Vite+Element Plus搭建。针对不同角色，前端做了差异化设计——买家访问移动端商城，商家和超级管理员等后台管理角色进入各自的后台管理页面，路由权限控制确保各角色只能访问自己的功能范围。后端采用Express框架构建API服务，通过JWT进行认证，保障角色权限的有效隔离。前端构建工具使用Vite来提升开发效率。
207: 数据存储方面，MySQL负责服装信息、订单、店铺和用户等核心业务数据的持久化；Redis作为权限缓存层提升系统响应速度；文件存储统一管理服装图片和详情图等非结构化资源。系统整体架构如图3-1所示。

391: 4.2.1 订单在线支付模块设计
392: 1、模块功能描述
393: 订单在线支付模块处理买家订单的支付流程。买家在订单确认页选择支付方式后提交支付请求，系统校验订单状态、支付金额匹配性及支付幂等性，调用模拟支付接口完成支付后记录支付信息、更新订单状态为已支付，并创建交易记录。
394: 2、输入项
395: （1）买家选择支付方式，单击"立即支付"，传入买家ID、订单ID、支付金额、支付方式。
396: （2）支付平台返回支付结果，传入支付状态和交易流水号。
397: 3、输出项
398: （1）支付成功后，页面提示"支付成功"，返回支付时间、交易流水号。
399: （2）订单状态更新为已支付，订单列表中显示"已支付"标签。
400: 4、实现方式
401: 买家在订单确认页点击"立即支付"按钮，选择支付方式后提交，系统将调用POST /mobile/payments/simulate接口。系统首先校验订单状态（待支付）和归属关系，验证支付金额与订单金额是否匹配，检查是否已存在支付记录。校验通过后调用模拟支付处理，生成交易流水号，更新订单状态为已支付，记录支付信息和交易流水，最后返回支付成功结果。

465: （3）买家可选上传图片，传入图片URL数组。
466: （4）单击"发布"按钮，提交社区内容创建请求。
467: 3、输出项
468: （1）发布成功后，页面提示"社区内容创建成功"，返回内容ID。
469: （2）社区列表页显示新发布的内容，包含标题、发布者、发布时间、浏览量。
470: （3）内容详情页展示完整正文、关联服装列表、图片和评论。
471: （4）关联服装以卡片形式展示，包含服装图片、名称和价格。
472: 4、实现方式
473: 买家在社区页面点击"发布内容"按钮，填写标题和正文后提交，系统将调用POST /api/discussions 接口。系统从JWT认证中获取买家ID，创建社区内容记录，获取内容ID。如果传入了服装ID数组，遍历数组依次创建内容与服装的关联关系；如果传入了图片URL数组，遍历数组依次创建内容与图片的关联关系。最后返回创建成功的内容ID。内容发布后自动进入社区列表，按置顶状态和创建时间排序展示。

478: 4.2.6 在线咨询服装模块设计
479: 1、模块功能描述
480: 在线咨询服装模块实现买家与客服之间的实时会话和消息收发功能。买家可选择客服发起咨询会话，系统检查是否已存在活跃会话（避免重复创建），创建新会话后双方可在会话中发送文本消息。系统记录消息发送者、内容、类型和已读状态，支持消息历史查询和未读消息统计。
481: 2、输入项
482: （1）买家单击"联系客服"，传入买家ID、客服ID。
483: （2）买家在会话中输入消息内容，单击"发送"，传入发送者ID、发送者角色、消息内容、消息类型。
484: （3）买家查看消息历史，传入会话ID、页码、每页条数。
485: 3、输出项
486: （1）会话创建成功后，进入聊天页面，显示会话ID。
487: （2）消息发送成功后，消息气泡显示在聊天窗口中，对方收到新消息通知。
488: （3）消息历史以时间顺序展示，包含发送者头像、消息内容、发送时间。
489: （4）未读消息数以角标形式显示在会话列表上。
490: （5）会话已关闭时自动重新开启，提示"会话已重新开启"。
491: 4、实现方式
492: 买家在服装详情页点击"联系客服"按钮，选择客服后提交，系统将调用POST /api/conversations接口创建会话。系统检查买家和客服是否存在，查询是否已存在活跃会话，如已存在则直接返回现有会话ID，否则创建新会话。买家在聊天窗口输入消息后点击"发送"，调用POST /api/conversations/:id/messages接口，系统检查会话状态（如已关闭则自动更新为活跃），创建消息记录，更新会话的更新时间戳，返回完整消息信息。消息发送后对方收到实时通知，可查看消息历史并标记为已读。

647: 5.3 测试结论
648: 本章节主要测试模块包括购买服装管理、服装管理、订单管理、店铺管理、用户管理、系统管理，使用测试方式包含错误推导、必填项测试、等价类划分法。本次测试共测试24例，其中测试成功16例，失败8例。失败的原因主要是表单必填项校验不足、业务逻辑校验缺失、边界条件未处理等问题。测试过程中发现的前端表单校验缺失、后端参数合法性校验不足等问题均已修复，并通过回归测试。系统目前已满足功能完整性要求，总体测试结果良好，符合预期的要求和标准。
649: 结  论
650: 依依大码服装在线销售系统面向大码消费群体，围绕服装购买、服装管理、订单信息管理等核心业务，为买家和商家搭建了在线交易平台。经过多轮测试与反复修改，系统已基本满足双方的日常使用需求，并能稳定运行。
651: 在设计与实现阶段，先对比了传统服装购买方式，分析了大码垂直电商的服务差异，进而明确了系统功能定位。技术方案采用Node.js与MySQL相结合，管理后台使用Vue.js配合Element Plus组件库，移动端基于uni-app实现跨平台适配。完成功能模块划分和开发后，通过功能测试对系统进行了验证，测试过程中发现的部分接口响应超时、移动端样式适配等细节问题均已逐一修复，最终使买家和商家的核心需求得到覆盖。
652: 总体来看，该系统实现了购买服装、订单管理、用户管理、店铺管理、服装管理和系统管理等核心功能，能够满足大码服装电商的基本需求。受非主观因素的限制，当前系统在用户交互体验上还有改进余地，如商品搜索功能可以更加精准，购物车流程可以进一步简化，个人中心页面的信息展示可以更加丰富。后续工作将重点围绕前端界面优化、表单验证完善、提示信息友好化等方向继续改进，同时考虑增加商品收藏分类管理、订单状态消息提醒等实用功能，为用户提供更加便捷、舒适的购物体验。
